## 三 认知修正（对既有理解的重要更新）

1. **"组装后卡死（滑块不回位）"≠ 正常现象** —— 它是 **4-in-1 hooks（pre3/r4/cvps/netx）的副作用**；干净环境拖动后一切正常（失败动画、重试均工作）。**影响**：s7 时代对"拖动后行为"的所有解读都要以"hook 副作用"为前提重审；正式攻坚时**抓取 hook 要与"提交时机"解耦**。
2. **题型已变更：PUZZLE（现行）≠ INPAINTING（capsolver 时代/r5 时代）** —— capsolver 的检测器/结论（"76/76 检测、F015=bot 检测"）**不直接适用于当前题**；本日已自研 PUZZLE 检测器。
3. **首页提交门槛**：页面**自认对齐后**才发起 verify（证据：对齐 232 → 提交；此前多轮未对齐（hook 环境）无提交）。**提交等待期**：拖动后 ~1s 内发出。
4. **错误码谱系（全）**：`T001`=通过；`F014`=无初始化记录/位置；`F015`=验证交互不通过；**`F001`=风控类（经验：~3 连 verify → ~10 分钟冷却）**——本日已消耗 2 次（F014 + F001）。
5. **网关层 vs 业务层**：所有提交（构造/重放）均获网关 `Code:"Success"`——**协议管道本身 0 壁垒**；难题收窄到"业务判定"（对齐质量/轨迹/环境）。
