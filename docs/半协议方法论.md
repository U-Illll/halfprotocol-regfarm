# 半协议方法论（half-protocol）

> 本文是本仓库的顶层方法论：什么是「半协议层」，它能做到什么、做不到什么，
> 以及把 5 个平台的实现做一个横向对照。

## 一、定义

> **半协议** = 利用对验证接口协议的逆向，**直接构造数据提交接口**（而非拖滑块交互）；
> 浏览器的作用仅剩两件事——**提供 token** 与**模拟正常用户环境**。

完整形态 = 三件套：

1. **视觉层**：确定滑块/缺口位置（纯定位，不输出文本；NCC / Chamfer / 形状匹配即可起步）；
2. **协议层**：用逆向出的接口协议**构造数据直接提交**（不执行拖动交互）；
3. **浏览器层**：负责 token（deviceToken / irToken / 一次性凭据）获取与正常用户环境伪装。

## 二、与另外两条路线的对照

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 纯交互自动化 | 驱动真实浏览器完成拖动/点击 | 门槛最低 | 轨迹检测、`isTrusted`、环境检测逐层加码；批量场景易被节奏风控 |
| **半协议（本仓库）** | 逆向接口后构造提交；浏览器只供 token/环境 | 触发路径与真客户端**逐字节一致**；核心链可离线复现/回归 | 需完成协议逆向；一次性凭据仍依赖页面 |
| 全协议模拟 | 完整离线伪造设备指纹 + 签名链 | 无浏览器依赖 | 工作量最大；设备指纹常为服务端签发，离线伪造往往死路 |

**结论**：半协议是收益/复杂度比最高的一层。浏览器不可脱离的部分（服务端签发的 deviceToken 等）恰好是页面天然提供的。

## 三、平台横向对照（本仓库五案）

| 平台 | 提交物形态 | 加密要点 | 浏览器侧还剩什么 | 完成度 |
|---|---|---|---|---|
| 易盾 | URL 参数 `data`（五字段合成） | 自研 64B 链式加密 + 私有 base64(pad=7) + XOR(token) | ir 凭据（一次性，页面侧抓） | 0 拖动协议直打 ✅ |
| 顶象 | 表单 `ac`（字段流） | `[type][len][XOR 变体加密]` + 私有字母表 base64 | 取题的点击（零拖动） | 0 拖动协议直打（含从零构造）✅ |
| 数美 | fverify 参数 | 无需纯算（服务端接受对齐拖动） | 全部交互（CDP 直连） | 对齐拖动 PASS ✅ |
| CAS（aj-captcha 版） | `pointJson` / `captchaVerification`（纯坐标） | AES-128-ECB(secretKey)，**无轨迹** | 无（纯 HTTP 同会话） | 纯坐标协议 ✅ |
| 阿里云 V2 | `CaptchaVerifyParam.data`（密文） | HMAC-SHA1 签名 ✅；`data` 组装函数靠**点火式**取引用 | deviceToken（服务端签发，必须页面供） | 签名/网关全通；点火式已命中 data 形态 ✅ |

## 四、工程要点（跨案例提炼）

1. **会话一致性**：取题 → 提交 → 登录/业务必须同一个 cookie jar / 同一进程，时间窗常常是**秒级**。
2. **一次性凭据管理**：token/rid/dt 这类服务端签发值，**每次运行全链一气呵成**，不要跨轮复用。
3. **提交次数预算**：多数平台对「同一 token 的提交次数」有硬限（易盾 2 次），调试要 dry-run 先行。
4. **出口与冷却**：风控码（F001 等）常与出口 IP 属性、连击次数强相关；
   「对齐正确仍被拒」优先怀疑出口，而不是继续调轨迹。
5. **环境最小化**：伪装以条件修补为主（`stealth/stealth-core.js` 哲学）——硬覆盖反而留指纹。
6. **离线可回归**：把加密链复刻为可离线重放的自检（易盾 `decrypt-verify.js`、顶象 `--selftest`、
   阿里云 `verify_sig.py`），每次改动先跑离线断言再上真打。

## 五、边界诚实清单

- 服务端**主动挑战型**设备指纹（服务端签发、请求时校验）不可能完全离线伪造——半协议把它保留给浏览器层。
- 协议参数会随 SDK 版本漂移：本仓库各案例记录了「版本自适应定位法」（如顶象的候选表 + 结构分型、
  阿里云的「模式搜索」组装点定位）。
- 视觉层只保证**坐标质量**：NCC / 形状匹配在低质量图上会有歧义，务必带置信度门槛与重取图策略。
