## 1. ac 结构分解

### 1.1 顶层
```
ac = "<ver4>#" + base64_std(binary)      ver4 ∈ {5948, 5879, ...}
```
| 项 | drag1 | drag2 | 说明 |
|---|---|---|---|
| ac_len | 1813 | 1793 | 含前缀 5 字符 |
| prefix | `5948` | `5948` | **两样本相同** |
| b64 body 长度 | 1808 | 1788 | **均 % 4 == 0** |
| 二进制长度 | 1354 B | 1341 B | body/4×3 |
| padding | `==` (2) | 无 | 合法 base64 |
| 字符集 | 65 符号 = 标准表 + `=` | 64 符号 | **无自定义字母表** |
| 字符 entropy | 5.7329 bit/ch | 5.7078 | max 6.0 → **chi2=795/844，强偏斜** |
| zlib(text) 比 | 0.5868 | 0.5766 | base64 文本本身已近高熵 |
| 字节 entropy | 7.384 bit/B | 7.416 | 全表 237/239 个不同字节 |

### 1.2 二进制分区（两样本交叉验证）
```
[0:8)      8 B   固定魔数/版本头   62 b5 e7 87 5b e8 ab 2e   ← 两样本完全相同
[8:12)     4 B   每请求变化        0d93 8cac  vs  01f9 922c   ← 唯一变化点(头部内)
[12:106)  94 B   环境指纹区        逐字节全同(94/94)          ← 同浏览器同一设备
[106:327/321)  ~220 B  会话区      两样本完全不同
[327/321 : +396)  12 × 33 B        记录段（结构同构）
[+631/+624)  尾部 13 × 48 B        drag2 恰好整除；drag1 = 13×48+7
```

**头部常量区 94 字节的复用结构**：offset 28..47 == offset 76..95（20 字节完全相同），offset 32..47/80..95 16B 全同，offset 28..31/76..79 全同 → 头部内部存在 **48 字节周期的重复**。

### 1.3 33 字节记录段（最强结构证据）
以常量块 `5d 70 b9`（base64 文本表现为 `XXC5`）为锚点反推记录起点：

- drag1: 起点 = 354-27 = **327**，12 条
- drag2: 起点 = 348-27 = **321**，12 条

两样本记录段**逐列画像**（`=` 同列同值）：

| 记录内偏移 | drag1 (12 条) | drag2 (12 条) | 判定 |
|---|---|---|---|
| +05 | `13 57 57 57 57 …` | `57 57 57 …` | d2-const |
| +06 | `1e 60 60 60 …` | `60 60 60 …` | d2-const |
| +07 | `6f f0 f0 f0 …` | `f0 f0 f0 …` | d2-const |
| +08 | `4c 9e 9e 9e …` | `a9 a9 a9 …` | d2-const |
| **+15..+19** | `8f c5 e7 27 54` ×12 | `8f c5 e7 27 5e` ×12 | **跨样本同族**（仅 +19 差 1 nibble） |
| +24 | `f9` ×12 | `f9` ×12 | 同 |
| +26 | `99`(11)+`d9` | `99`(11)+`d9` | 同 |
| +27..+30 | `5d 70 b9 f8` ×12 | `5d 70 b9 91` ×12 | 同族（+30 不同） |

`8f c5 e7 27 54` 的 base64 = **`j8XnJ1Q`** —— 正是统计中 drag1 出现 12 次、drag2 出现 11 次的 6-gram。这是"常量列 ↔ base64 重复块"的闭环证明。

**nibble 级发现**：大量列呈"高 4 位恒定 / 低 4 位变化"或反之，例如
```
+03: 8f | d6 d7 d7 d7 d7 d7 d7 d6 d7 d6 d7 d6   （高 nibble 恒 d）
+04: 52 | b5 c5 c5 c5 c5 c5 c5 b5 c5 b5 c5 b5   （低 nibble 恒 5）
+15: 8f×12  +16: c5×12  +17: e7×12  +18: 27×12  +19: 54×12  （高低双 nibble 全恒定）
```
→ 字段**按 nibble（4 bit）粒度**分布；33 B/条里 10 条为常量列（drag1）/4 条（drag2），列平均条件熵仅 1.49 bit/byte（真随机会是 8）。

### 1.4 尾部 48 字节块
- drag2 尾部 624 B = **13 × 48 精确整除**
- 周期扫描：reclen=48 得分 0.1892（随机基线 0.0538），优于 33 的 0.1633
- 48 B = 3 × AES 块长度（供参考）
- 48B 列的典型模式：值域高度集中在 `0x22/0x44/0x62/0x94/0xb7/0xac/0x9e/0x69/0x5b/0xba` 等，**低 5 位（或低 6 位）相同、高 3 位（高 2 位）变化**：
  ```
  0x22 0x62 0xa2 0xe2  低6位全 = 0x22 ('i' 索引)
  0x94 0xb4 0x64 0x44  低5位全 = 0x14
  ```
  → 又一处"定长前缀位 + 变化数据位"的打包痕迹。

## 2. `5948` 的含义（假设 + 证据）

### 假设 H（采纳）：`<4位数字>#` 是**生成该 blob 的 SDK 模块的版本号**（"v1.<4位>.<build>" 序列）

**支持证据**
1. **同机制的实测锚点**：`dx-drag1-net.json` 中 `constid.dingxiang-inc.com/udid/c1` 请求头 `Param: 5879#<base64 284字>`；而同一批 `bodies/body-001.txt`（constid-js 响应）首行注释为 `/*! v1.5879.0(6393) 2026-10-05 19:10:02 … */` —— **5879 与 constid-js 版本号精确相等**。这证明 `<4位数字>#` 的前缀位在该体系中确实承载"模块版本号"。
2. 格式完全同构：`Param` 与 `ac` 都是 `<4位>#<标准 base64>`，且 body 长度均是 4 的倍数（284、1808、1788）。
3. constid 版本在两次抓取间从 `v1.5879.0(6393)` → `v1.5880.0(6394)`，编号单调递增 + build 号 +1 → 该 4 位序列是**活跃递增的版本号空间**，5948 落在其中（5948 > 5880 亦符合"滑块 SDK 比 constid 迭代更快"）。
4. `5948` 在两样本间**完全相同**——不同 sid、不同 aid、不同拖拽、相隔 591111 ms，排除"与时间/sid/通道绑定"。它只能是客户端侧常量：版本号 or 密钥 id。

**反证 / 未闭合项**
- ✗ `5948` 在所有已抓 SDK 文件（`captcha-ui-v5-index.js`、`oneclick-Captcha-js-5.1.53.js`、`constid-js-index.js`、`greenseer.js`、`site-*.js`）中 **0 命中**。生成 ac 的模块（或其常量表）未落在本批 SDK 快照内 —— 该模块大概率是**动态加载/内联**的。
- ✗ 无法排除"服务端密钥索引 key id"这一竞争假设（两者都会表现为"客户端常量"）。

**判别实验（给 hook 线，最小成本）**
- **D1 换 ak**：用另一站点 ak 抓 ac，看前缀是否变化。变 → 与站点/密钥绑定（key id）；不变 → 客户端版本常量。
- **D2 跨天采样**：隔 1~3 天再抓同一站点，变 → 版本号（SDK 自动更新）；恒定 → key id / 长期常量。
- **D3 前缀替换**：hook 到 ac 后把 `5948` 手改为 `5949`/`5879` 再发出，观察响应类别。若服务端报"格式/签名错误"→ 前缀参与密钥选择；若仍返回 `retry`→ 前缀只是标签。

## 4. retry / 评估机制与 oracle 设计

### 4.1 已捕获的服务端评估响应（两种失败态）

| 样本 | 响应体 | 前端表现（同批 log） |
|---|---|---|
| drag1 | `{"success":false,"token":null,"msg":"请求超时","tp":null,"sv":null,"retry":0,"ot":1}` | +1s：`stateText="加载失败 请点击重试"` |
| drag2 | `{"success":false,"token":null,"msg":"retry","tp":null,"sv":null,"retry":1,"ot":null}` | 全程 `stateText="智能检测中"`（未失败） |

响应字段全集（来自 `/api/a` 与 `/api/v1` 同体系）：`success token msg tp sv retry ot`（`/api/a` 另有 `sid cid y p1 p2 p3 type logoSwitch ot result bc …`）。

**语义解读（假设）**
- `retry=1` ⇔ **服务端已成功解析 ac 并完成了一次轨迹评估**，结论是"要求重试"（非硬拒）。这是**最有价值的中等强度 oracle**：任何改动只要仍能把 `retry` 保持在 1，就说明 ac 的"可解析性"未被破坏。
- `msg="请求超时", retry=0, ot=1` ⇔ 另一类失败（时效/上下文不匹配），**不是解析失败**（否则会给出格式类 msg）。`ot` 字段疑似超时/一次性标志。

**关键差异线索（时序）**
- drag2：sid 由 `dx-1791254897108-7013090-1` 生成 → POST 于 `dx-1791254922626-37899156-3`，间隔 **25.5 s**（< 30 s）→ 得 `retry:1`
- drag1：sid 由 `dx-1791254331515-6147815-3` 生成；POST **复用同一个 aid**（ts 完全相同），即 aid 的 ts 与 POST 同戳 → 得 `"请求超时"`
→ 支持"**aid/sid 有效期 ≈ 30 s**，`ot=1`/超时判定与 aid 时间基准强相关"的假设。

### 4.2 最小成本 oracle 设计（供 hook 线执行）

> 目标：把 `{"msg","retry","ot"}` 当作 **1~3 bit 的差分信道**，用最少请求数反推字段语义。

**R0 黄金基线（必做第一步）**
真实通过一次（`success:true, token != null`）并保存完整 ac。此后所有实验都有三条基线的差分：`success / retry:1 / 请求超时`。

**R1 时效标定（约 8 次请求）**
固定同一 sid，同一拖动，分别在 t = 0.5 / 2 / 5 / 10 / 20 / 25 / 29 / 31 / 60 s 提交 →
输出 `t → (msg, retry, ot)` 阶梯表，直接测出 aid/sid 有效期与 `ot` 语义。

**R2 单字节消融（约 12 次请求）** —— 定位"被校验字段"
在 hook 里拿到 ac 后，按区段各改 1 字节再发：①前缀数字 ②offset 8（每请求变化字节）③offset 20（指纹区）④记录段 +15（跨样本常量列）⑤记录段 +20（变化列）⑥尾部 48B 块 ⑦base64 长度 -4（截断）。
判据：响应退化为"格式/签名错"→ 该段被完整性校验；仍 `retry=1` → 该段可自由构造。

**R3 前缀语义（3 次请求）**
前缀替换 `5948→5949` / `→5879` / `→0000`；若全部仍返回 `retry=1` → 前缀仅为版本标签（H 成立）；若报错 → key id。

**R4 重放与随机性（4 次请求）**
同一 ac 原样连续重放 3 次：若第 2/3 次从 `retry:1` 变为"已使用/超时" → 有一次性 nonce；若稳定 → ac 无重放保护（对"协议直打"极大利好）。

**R5 时间戳探测（约 10 次请求）**
拖动时长扫描（0.3 / 1 / 3 / 6 / 12 s）与提交延迟扫描交叉，观察 `ot` 何时变 1 → 定位服务端的时间一致性窗口。

**采集要求**：每次请求同时记录 `{ac, sid, aid, x, y, 客户端 ms 时戳, 响应 JSON}` 到 JSONL —— 这是后续统计（而非单点）推断的必要条件。

## 5. 会话时序规律

### 5.1 事件时间线（全部同批抓包，跨度 730.2 s ≈ 12.2 min）

| 事件 | aid | seq | ts(ms) | Δt |
|---|---|---|---|---|
| api/a | `dx-1791254192453-85117419-1` | 1 | …192453 | 0 |
| api/a | `dx-1791254193108-24273989-2` | 2 | …193108 | +0.655 s |
| api/a | `dx-1791254317035-69831998-1` | 1 | …317035 | +124.6 s |
| api/a | `dx-1791254317108-67216974-2` | 2 | …317108 | +124.7 s |
| api/a | `dx-1791254331515-6147815-3` | 3 | …331515 | +139.1 s |
| **POST /api/v1 (drag1)** | `dx-1791254331515-6147815-3` | **3（复用）** | …331515 | +139.1 s |
| api/a | `dx-1791254664084-85561408-4` | 4 | …664084 | +471.6 s |
| api/a | `dx-1791254896518-98344667-2` | 2 | …896518 | +703.1 s |
| api/a | `dx-1791254897108-7013090-1` | 1 | …897108 | +703.7 s |
| **POST /api/v1 (drag2)** | `dx-1791254922626-37899156-3` | 3 | …922626 | +730.2 s |

### 5.2 规律
1. **aid = `dx-<ms 时间戳>-<6~8 位随机>-<seq>`**；`seq` 是**每 ak（站点）独立的请求计数器**：`26ba29b6…` 走 1,2；`dxdxdxtest…` 走 1,2；`99de95ad…` 走 3,3,4（跨页面重新从小数起）。
2. **同一"验证轮次"内 api/a 与 POST /api/v1 共享同一个 aid**（drag1 的 api/a 与 POST aid 逐字段相同），POST 后再发 api/a 则 seq+1 → **aid 标识"一轮验证"，而非单次请求**。
3. **sid 由 `/api/a` 下发，生命周期 < 30 s**：drag2 实测 sid 到 POST 间隔 25.5 s 仍可用（`retry:1`）；drag1 同戳提交反而得"请求超时" → 说明还存在除 sid 年龄外的第二时间因子（很可能 ac 内部编码了自 t0 起的相对时间线）。
4. `cid=74729939` 全程恒定（浏览器/设备维度的客户 id，与 sid 解耦）。`c`（udid）在 drag1/drag2 相同 → 同一设备；`/udid/c1` 返回 `{"msg":"token valid","rt":0/1}` 表示 udid token 校验通过。
5. 题型会被 `/api/a` 动态切换（`type: 0 / 1 / 12 / 4`；`type=4` 附带 `verifyType=1, imgName:"plane", color:"blue"`），**同一 ak 连续两次 api/a 可能给出不同题** → 协议直打需按 `type` 分支。

## 6. ac 长度 vs 轨迹长度（否证）

| | drag1 | drag2 | 生成脚本 |
|---|---|---|---|
| DELTA（位移 px） | 220 | 76 | `dx_13_drag.mjs` / `dx_18_drag2.mjs` |
| steps（mouseMoved 次数） | 34 | 36 | 同上 |
| 单步间隔 | 24+rand(0..18) ms | 22+rand(0..16) ms | — |
| 缓动 | `1-(1-p)^3` | `1-(1-p)^3` | — |
| POST x (px) | 240 | 96 | — |
| **ac_len** | **1813** | **1793** | — |

**结论：假设"ac 长度 ∝ 轨迹长度"在两个样本上【不成立】**——
- 位移相差 2.9 倍、步数还多 2 步，ac 仅长 20 字符（1.1%）；
- 差异 **全部**来自头部（+6 B）与尾部（+7 B），**记录段两边都是 12×33 B**；
- 因此长度差异更像"头部/尾部的变长字段"（疑似与题型/图片/结果集相关）而非轨迹点数。

**注意**：样本仅 2 个且 DELTA 差异小，属**弱否证**。建议 hook 线做参数扫描（DELTA ∈ {30,80,150,240,320} × steps ∈ {8,34,80}）建立 `len(DELTA, steps, duration)` 表再定论。

## 7. "加密 vs 编码"判定汇总

| 判据 | 强加密(AES/流)预期 | 实测 | 判定 |
|---|---|---|---|
| 跨会话逐字节相同区段 | 不应存在（除非 keystream 复用） | 头 94 B **完全一致** | 倾向编码 |
| 记录段列常量 | 不应有（ECB 例外） | 10/33 列恒定（drag1） | 倾向编码 |
| base64 字符分布 | 均匀，chi2≈63 | **chi2=795 / 844** | 强烈偏离 |
| 位分布 | 各位 ≈0.5 | bit5(0x20) = **0.5827 / 0.5563**（z≈+17） | 有偏斜 |
| nibble 结构 | 无 | 大量"高 nibble 恒/低 nibble 变" | 位打包痕迹 |
| 已知值(udid/sid/ak)明文 | 不应出现 | 确实不出现 | 中性（可能被哈希/位混淆） |

**结论（措辞保守）**：ac 的 `#` 后数据是**结构化二进制经标准 base64 编码**，具有可辨识的**定长记录（33 B）与定长块（48 B）**、**nibble 级字段**、以及**跨会话/跨记录的大面积字节复用**。这**排除"整体 AES-CBC 强加密"**，但不能排除"(a) 每字段哈希/位混淆" "(b) 分组粒度(16 B)的 ECB 类弱加密"。**这是对"协议直打"最有利的结论**：结构可逆、可构造。

## 8. 建议（按优先级）

1. **P0 交给 hook 线的 3 条即验预测**（改一次 hook 即可验证/推翻本报告核心）：
   - **P1**：`btoa` 被调用时，其返回值应 **精确等于** ac 的 `#` 后部分 → 直接证明 `ac = prefix + "#" + btoa(bin)`；
   - **P2**：`btoa` 输入（latin1）转字节后，应能在 offset ~327 处观察到 **间隔 33 的重复结构** 与常量序列 `8f c5 e7 27 54`；
   - **P3**：ac 拼接处的常量 `5948` 应能在某个作用域找到其来源变量（全局常量 / 配置下发 / 模块 build 号）——直接结案 §2 的假设。
2. **P0 跑 §4.2 的 R0+R1+R3**（约 15 次请求）：拿到黄金基线 + 时效阶梯 + 前缀语义，立刻把 oracle 从"是否 retry"提升为"字段级差分信道"。
