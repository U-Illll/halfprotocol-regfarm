## 0. 一句话结论

易盾 `data.d/m/p/f/ext` 与 `cb` 的外层**不是加密而是"自定义表 base64"**；真正的加密是自研 64 字节分组算法 `yd_aes`，
其常量（自定义 64 字符字母表、padding 字符 `7`、S 盒、种子密钥）**明文硬编码在 SDK 里**，
因此可完全离线还原 / 本地伪造。已实现**双向可逆**的 Python 解码器与打包器。

## 2. 【必达】尾字符 `7` 专题 —— 结论：**自定义 base64 的 padding 字符**

### 2.1 直接证据（来自 SDK 源码，非推断）

`core-optimi.m25b40.v2.28.5.min.js` 字符串表 idx 559/561 明写：

```js
__BASE64_ALPHABET__ = "MB.CfHUzEeJpsuGkgNwhqiSaI4Fd9L6jYKZAxn1/Vml0c5rbXRP+8tD3QTO2vWyo"   // 64 字符，含 '.'
__BASE64_PADDING__  = '7'                                                                 // 不在字母表内
```
`base64EncodePrivate`（`_0x491e42`）默认即用这两者 → **`7` 就是 `=` 的替代 padding 字符**。

### 2.2 假设检验（逐一排除）

| 假设 | 判定 | 证据 |
|---|---|---|
| H1 `7` 是 padding 替代 | **✅ 成立** | SDK 常量直证；`7`∉字母表；只出现在尾部 |
| H2 `7` 是校验字符（如 CRC 尾标记） | ❌ 反证 | k%3==2 的密文完全无 `7`（见 2.3），校验字符不可能整体消失 |
| H3 `7` 是截断标记 | ❌ 反证 | 尾部 `7` 个数为 1 或 2，与截断语义不符；且尾部连续数量恰好等于 `(3-n%3)%3` |
| H4 固定尾字节（加密后末字节低 6 位恒定） | ❌ 反证 | 若为真，则末字节低 6 位恒 = 59。但采样 8 条 k%3==2 的密文，尾字符覆盖 8 种不同值 |
| H5 位对齐（补零产生固定值） | ❌ 反证 | 补零 4 bit 只可能产生值 ∈{0,16,32,48}，补 2 bit 只可能产生 4 的倍数；标准表下 `59` 两者皆不满足 |

### 2.3 长度规律与 `7` 的精确关系（可证伪预测，已实测验证）

密文原始字节 `n = 4 + 64k`，则：

```
padding 个数 = (3 - n%3) % 3 ,   n%3 = (1+k) % 3
  k ≡ 0 (mod 3)  →  n ≡ 1  →  **2 个 '7'**（结尾 "77"）
  k ≡ 1 (mod 3)  →  n ≡ 2  →  **1 个 '7'**
  k ≡ 2 (mod 3)  →  n ≡ 0  →  **0 个 '7'（尾字符随机！）**
```

**实测（`07_tail7.py`）**：

| 组 | 样本数 | 末端字符集合 | 是否符合预测 |
|---|---|---|---|
| k%3==0 | 8 | `['7']` | ✅ |
| k%3==1 | 8 | `['7']` | ✅ |
| k%3==2 | 8 | `['1','E','I','M','R','W','r','z']` | ✅（无一为 `7`） |

真实样本端同样吻合：drag2 的 `d`（k=9，9%3==0）以 `ng77` 结尾（**2 个 7**），其余 k%3==1 的以 `x7` 结尾（1 个 7）。
`07_tail7.py` 对 10 条真实样本的 `trail7 == pred_pad` 全部 ✅。

> **修正上一轮侦察的前提**："所有密文尾字符固定 `7`"是**统计现象**而非必然规律；
> 当 `k ≡ 2 (mod 3)` 时密文无 padding、尾字符随机。这反而是 `7`=padding 的最强证据。

## 3. 【必达】编码器判定

### 3.1 判定结果

**外层 = 自定义 64 字符表 base64（位打包与标准 base64 完全一致，仅换表 + 换 padding 字符）。**
标准表/URL-safe 表直接解码会失败或产出乱码（因为 `.` 不在标准表）；**必须使用私有表**。

第 2 层（`d/f/ext/p` 的中间层）= **另一套 base64**（公开表 `i/x1XgU0z7k8N+lCpOnPrv6\qu2Gj9HRcwTYZ4bfSJBhaWstAeoMIEQ5mDdVFLKy`，padding `3`）。

### 3.2 熵/结构检验（`08_entropy.py`）

| 层 | 熵（bit/符号） | 判读 |
|---|---|---|
| 密文串（外层） | 5.40 ~ 5.97 | 理论上限 `log2(64)=6` → **均匀，编码特征** |
| 私有表 base64 解码后字节 | **5.70 ~ 7.66** | 理论上限 8 → **高熵，加密特征** ✅ |
| yd_aes 解密后中间层 | 2.00 ~ 5.05 | 文本 base64 |
| 内层解码后最终明文 | 1.50 ~ 3.34 | 结构化文本（数字/逗号） |

**结论**：外层是编码、内层是加密 —— 与"`yd_aes` + 自定义 base64"的结构判断一致。

## 5. 【争取】结构发现 —— 全字段明文已出土

### 5.1 三层解码链

```
URL 参数 → 私有表 base64 解码 → yd_aes 解密 → [中间层文本]
                                                ↓ 若是 xorEncode：公开表 base64 解码 → XOR token
                                             最终明文
```

### 5.2 各字段真实明文（drag1 / drag2）

| 字段 | 中间层 | 最终明文 | 含义 |
|---|---|---|---|
| **d** | `aes(采样轨迹.join(':'))` | `6,0,467,1 \| 9,-1,492,1 \| 13,-1,510,1 …`（36 点）<br>`4,0,132,1 \| 9,0,518,1 \| …`（31 点） | 每点 `x,y,t,isTrusted`，x/y 为相对位移与纵向抖动（px），t 为 ms 时间戳 |
| **p** | `aes(xorEncode(token, pct))` | `'51.87500000000001'` / `'75'` | 滑块位置百分比 = `parseInt(jigsaw.left)/width*100` |
| **f** | `aes(xorEncode(token, feat))` | `35,3,-0.2222,0.5827,36,-0.007,0.4167,0.2358,0.0864,23,…` | 以整数（时间差）分段的运动特征序列（速度/加速度类，4 位小数） |
| **ext** | `aes(xorEncode(token, 'a,b'))` | `'1,36'` / `'1,31'` | `mouseDownCounts, traceData.length` |
| **cb** | `aes(32字符)` | `EvkE8gSYLsfpnvAkqDy1cnOH5G4f8Iy6`<br>`Bv5MCwpGibf1nv9Mrymae6pePz4uvVh6` | 32 位随机 `[0-9A-Za-z]`，6 个固定位置写入水印 |

**内部一致性校验（强证据）**：
`ext` 声明的轨迹长度与 `d` 的实际点数**逐样本一致**（drag1: 36=36；drag2: 31=31）。
这个数字在解密前不可能被猜测到 → 解码结果唯一且正确。

### 5.3 `cb` 水印（`_0x62692`）

```js
cfg = {suffix:'m25b40', code:'vfnv46', pos:[1,10,12,13,26,31]}
u = uuid(32)                       // '0-9A-Za-z'
for i,ch in code: u[pos[i]] = ch
```
两个真实样本的 6 个 pos 位字符 = `vfnv46`，**完全命中** ✅（`非水印位字符集` 均为 `[0-9A-Za-z]` 子集，无线索泄漏）。

### 5.4 `iv=4` 假设 —— **已证实**

```js
_0x20772d['IV_VERSION'] = 0x4;      // 常量
_0x179b39 = _0x59412f['IV_VERSION']; // store 注入 → URL 参数 iv
```
`iv` 是**硬编码常量 4**，与加密无关（既不参与 `yd_aes`，也不是 IV 长度/迭代轮数）。本地直打时固定填 `4` 即可。

### 5.5 长度公式（可直接用于预测密文长度）

```
k = ceil((len(明文)+8+4)/64) 的精确形式：
  M = len(utf8(明文)) + 8            # +8 = CRC32 的 hex 字符串占 8 字节
  padLen = (M%64 <= 60) ? 64 - M%64 - 4 : 128 - M%64 - 4
  n = M + padLen + 4 ;  k = n/64
  密文字符数 = 4*ceil((4+64k)/3) ;  尾部 '7' 数 = (3 - (4+64k)%3) % 3
```
实测：drag1 `d` 明文 580 B → 860 字符（k=10）✅；drag2 `d` 明文 564 B → 776 字符（k=9）✅。

## 6. 【争取】协议直打可行性（已建打包器并自校验）

`yd_pack.py` 可本地生成完全合规的 `data` 与 `cb`，并已用自身的解码链回读验证：

```python
token = '2a041cf5632744d68ced0787b79abdc7'
data  = build_check_payload(token, trace=[(4,0,132,1),(9,0,518,1),...],
                            slide_pct='75', mouse_down=1)      # → {d,m,p,f,ext}
url   = build_check_url({... 'dt':..., 'id':..., 'token':token, 'data':data, 'cb':gen_cb_plain()})
```
回读自校验：`d→['4,0,132,1', …]  p→'75'  f→'1,1'  ext→'1,4'  cb 水印=True`，CRC 全过 ✅。

**直打所需的其余输入**（本线未解、需他线补齐）：
1. `token` / `id` —— 来自 `/get` 接口（每会话）；
2. `dt`（deviceToken）—— 来自 `getDeviceToken()`，可能有本地算法或需从 `/get` 响应提取；
3. 轨迹内容 —— 必须**通过服务端行为风控**（时间单调递增、x 单调、含真实纵向抖动与 `isTrusted=1`）；
4. `f` 特征串 —— 目前可用最小合法值占位，但风控可能校验其与轨迹的一致性（**风险点**）。

## 7. 建议（按优先级）

1. **直打 MVP**：用 `yd_pack.py` + 真实一次 `/get` 的 token/id/dt，先构造 **单点/粗轨迹** 请求，观察 `result` 与 `error/msg`，逐步逼近真实轨迹密度。（高风险点是 `f` 的一致性校验）
2. **补齐 `dt`**：`dt` 是独立子系统（`getDeviceToken`），建议新开一线专攻其生成算法，否则每次直打都需先跑一次浏览器 `/get`。
3. **`f` 特征逆向**：把 `f` 明文与 `atomTraceData` 对齐，逆出其特征公式（本次已确认格式：`整数分段 + 4 位小数特征`），这是风控能否通过的关键。
4. **复用产物**：`round2-static/deob-strings.js` + `round2-data/yd_crypto_extracted.js` 已把 SDK 的字符串混淆层完全剥掉，后续任何静态分析请直接在这两个文件上做（比在 min.js 上 grep 高效一个数量级）。
5. **文档同步**：`FORMAT.md` 可直接作为协议直打线/顶象对比线的共享规范。
6. **注意版本**：本轮常量取自 `2.28.5`。若服务端换版本，`__SBOX__/__SEED_KEY__/__ROUND_KEY__/__BASE64_ALPHABET__` 可能变化，需重新提取（脚本 `03_extract_consts.py` + `04_extract_node.py` 可一键复跑）。
